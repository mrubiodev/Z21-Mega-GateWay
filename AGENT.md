# AGENT.md — Contexto para agentes de IA en este repositorio

Este archivo da contexto rápido a cualquier agente de IA (Claude Code u otro) que trabaje en este repo, para no repetir decisiones ya tomadas ni romper prioridades del proyecto.

## Qué es esto

Firmware de un emulador Z21 sobre una placa combo Mega2560+ESP8266, pensado para funcionar como esclavo XpressNet de una Roco MultiMaus standalone. Ver `docs/Z21_EMULATOR_SPEC.md` para el spec funcional completo — léelo antes de tocar código.

## Prioridad nº1, no negociable

**El objetivo más importante ahora mismo es que la app Z21 oficial reconozca el dispositivo como una central legítima.** Antes de tocar tracción, XpressNet real o pantalla, cualquier cambio debe mantener funcionando el handshake mínimo (ver sección 5 del spec):
`LAN_GET_SERIAL_NUMBER`, `LAN_GET_HWINFO` (HwType `0x00000201`), `LAN_X_GET_VERSION`/`LAN_X_GET_STATUS`, `LAN_GET_CODE` (`Z21_NO_LOCK`).

Si una tarea puede romper este handshake, avisa explícitamente antes de aplicarla.

## Seguridad — no negociable

El **botón de parada de emergencia** debe seguir siendo una interrupción hardware que dispara `LAN_X_SET_STOP` de forma inmediata, sin pasar por el bucle de menú ni por ninguna cola de eventos que pueda bloquearse. Ningún cambio de refactor debe introducir latencia ni dependencias ahí.

## Decisiones de arquitectura ya tomadas (no las reabras sin motivo)

- **Base de código de referencia**: `Digital-MoBa/DCCInterfaceMaster` (Philipp Gahtow), no la rama antigua de Arduino Uno.
- **Reparto de UART**: Serial3 (pines 14/15) para el enlace Mega↔ESP8266 (fijo por DIP switch de la placa, no es libre); Serial1 o Serial2 para RS485/XpressNet; Serial0 libre para USB/debug.
- **Framing del enlace Mega↔ESP (v0.4)**: `[SYNC0=0xAA][SYNC1=0x55][TYPE(1)][LEN(1)][payload][CHK(1)]`, ya no `[TYPE][LEN][payload]` a secas. Motivo: sin bytes de sync ni checksum de framing, un solo byte corrupto/perdido en el enlace físico desincronizaba la máquina de estados para siempre — todo lo que llegaba después se interpretaba con el offset equivocado (síntoma real observado: frames decodificados como `type=0x01 len=0x00` de forma repetida y estable con tráfico real de por medio). Ahora, si el checksum no cuadra, el frame se descarta y se vuelve a buscar `0xAA 0x55` en el flujo — se autorrecupera solo. `CHK` es XOR de TYPE+LEN+payload, y es distinto del checksum del protocolo Z21 (ese va dentro del payload). Si se cambia este framing, actualizar los dos sketches a la vez o se rompe la comunicación entre ambos.
- **Sincronización inicial Mega↔ESP (v0.4, payload NetInfo ampliado en v0.9)**: antes de que el ESP levante el UDP Z21, hay un handshake: el Mega manda `FRAME_TYPE_HELLO` cada 300 ms hasta que el ESP contesta con `FRAME_TYPE_NET_INFO` (modo STA/AP, IP local, IP de la puerta de enlace/gateway, MAC efectiva de la interfaz y SSID — pensado para que la futura pantalla TFT sepa qué mostrar sin duplicar lógica de red), y el Mega confirma con `FRAME_TYPE_SYNC_ACK`. Hasta que el Mega no manda el ACK, el ESP no reenvía tráfico UDP real hacia/desde él. Si no se completa en 8 s (`SYNC_TIMEOUT_MS`), el Mega sigue igual en modo degradado (LED código 5 = `STATUS_SYNCING` mientras dura) — nunca se bloquea esperando para siempre. Si el Mega se reinicia (p.ej. watchdog) y vuelve a mandar HELLO, el ESP contesta sin volver a cortar el UDP que ya estaba funcionando. NOTA v0.9: hasta esta versión el payload de NetInfo solo llevaba el byte de modo -- el resto del formato (`ip`/`ssid`) estaba documentado en `z21_protocol.h` pero `buildAndSendNetInfo()` nunca lo llegaba a rellenar (código muerto) y el Mega lo leía con valores a 0. Ahora sí se manda completo, más gateway y MAC (`NET_INFO_MAC_LEN`, la MAC que tenga aplicada de verdad la interfaz según `applyMac()`, no la de fábrica). El gateway y la MAC recibidos no se pintan en la cabecera de la pantalla (no cabe más sin competir por espacio, igual que ya pasaba con el SSID) — quedan en el log de comunicación (`displayLogf()` en `handleNetInfo()`, `mega_z21.ino`) y por `DEBUG_SERIAL`.

- **Diagnóstico y watchdog**: el Mega manda un heartbeat cada 1s (uptime, tiempo de ciclo medio/máximo, RAM libre, contadores de frames OK/error, versión de firmware propia, código de estado) y tiene un watchdog hardware (`wdt_enable`, timeout 4s) que lo autorresetea si `loop()` se cuelga. El ESP usa el heartbeat para saber si el Mega está vivo y lo muestra en la web de configuración — si no llega heartbeat, la web avisa explícitamente (revisar DIP switch/selector RXD3-TXD3/baudios/cableado) en vez de fallar en silencio.
- **Versionado interno**: `MEGA_FW_VERSION_MAJOR/MINOR` y `ESP_FW_VERSION_MAJOR/MINOR` en `z21_protocol.h` — NO es la versión que se declara a la app Z21 (esa es la de `LAN_GET_HWINFO`), es solo para nosotros, para saber qué firmware está cargado en cada chip. Subir el número al hacer cambios significativos en cada sketch.
- **LED de estado (pin 13 del Mega)**: parpadea en un código de N veces + pausa larga, N = código de estado (`STATUS_*` en `z21_protocol.h`): `1`=todo bien, `2`=nunca ha llegado un datagrama Z21 válido, `3`=hay frames corruptos, `4`=el último arranque fue un reset del watchdog (el firmware se colgó), `5`=sincronización inicial con el ESP en curso (ver "Sincronización inicial Mega↔ESP" más abajo). Parpadeo de 1 = normal.
- **Hardware físico de esta placa concreta**: además de los 8 DIP switches, hay un **selector físico separado** (serigrafiado "RXD0 TXD0" / "RXD3 TXD3") que decide a qué UART del Mega se conecta el ESP cuando el DIP está en modo MCU↔ESP. Tiene que estar en posición RXD3/TXD3 para que coincida con `LINK_SERIAL = Serial3` del firmware — es la causa más probable si el heartbeat nunca llega aunque el DIP esté bien puesto (1 y 2 ON, resto OFF).
- **Sniffer del enlace Mega↔ESP (v0.7)**: en `/sniffer` en el ESP, activable bajo demanda. El contador de bytes crudos (`totalRawBytesFromMega`) siempre está activo y es la señal más básica: si nunca sube, no hay comunicación física en absoluto (fallo de switch/cableado/baudios), independientemente de si el framing/protocolo es correcto. Desde v0.7 el sniffer ya no decodifica offline un único sentido a partir de bytes crudos: `sniffRecordFrame()` registra cada trama ya decodificada (tipo, payload) en el instante en que se procesa, en ambos sentidos (`SNIFF_DIR_RX_FROM_MEGA` dentro de `tryReadFromMega()`, `SNIFF_DIR_TX_TO_MEGA` dentro de `sendToMega()`), y si el tipo es `FRAME_TYPE_Z21` se decodifica además el header Z21 real (`z21CommandDescribe()`: `LAN_GET_SERIAL_NUMBER`, `LAN_X`, etc. — solo los headers que ya son fuente de verdad en `z21_protocol.h`). La vista `/sniffer?raw=1` con bytes crudos de un solo sentido se mantiene aparte, sin tocar, para el diagnóstico más básico de capa física.
- **Log de eventos con niveles (v0.7)**: `evLogf()` sigue existiendo tal cual (nivel INFO por defecto) para no romper las llamadas existentes; `evLogfL(nivel, ...)` añade nivel explícito (`LOG_LVL_WARN`/`LOG_LVL_ERROR`) para lo que sí requiere atención (timeout de WiFi, fallo de checksum de framing, MAC inválida). `/log` permite filtrar por nivel (`?level=warn`/`?level=error`), limpiar la vista (`?clear=1`) y exportar en JSON (`?format=json`) sin tocar el Serial en ningún caso (ver nota de cabecera del sketch).
- **MAC de red configurable (v0.7, prefijo por defecto 84:2B:BC desde v0.8)**: pensada para evitar colisiones cuando haya varios ESP en la misma red (satélites WiFi futuros, placas de pruebas). Se guarda en EEPROM (`EEPROM_ADDR_MAC_FLAG`/`EEPROM_ADDR_MAC`) y se aplica con `wifi_set_macaddr()` a STA y AP por igual en `applyMac()`, llamada justo después de `WiFi.mode(...)` y antes de `WiFi.begin()`/`softAP()` — el orden importa, según el SDK de bajo nivel del ESP8266. Desde v0.8, mientras no haya MAC personalizada guardada, **no** se deja la MAC de fábrica del chip: `applyMac()` genera y aplica siempre una MAC con el prefijo (OUI) fijo `84:2B:BC` (`generateDefaultMac()`), con los 3 bytes finales derivados del chip ID (estable entre reinicios, distinta por placa) — así todo lo que arranca en esta red se reconoce por el prefijo sin tener que configurar nada. Se sigue pudiendo fijar cualquier otra MAC (incluso con otro prefijo) desde el formulario de `/` (campo `mac`, vacío = vuelve a la MAC por defecto 84:2B:BC), con un enlace para sugerir una MAC aleatoria "localmente administrada" (bit `0x02` del primer byte) que por convenio IEEE 802 nunca coincide con una MAC de fabricante real.
- **Bug corregido en el framing del ESP y del Mega**: la primera versión de `tryReadFromMega()`/`tryReadFrameFromESP()` en ambos sketches consumía el byte TYPE antes de confirmar que el payload había llegado completo, desincronizando el framing en cuanto un frame llegaba repartido en varias vueltas de `loop()`. Se sustituyó en los dos por una máquina de estados (`LinkState`) que no consume nada hasta tener el frame completo. Si se toca esta función en cualquiera de los dos sketches, no reintroducir ese patrón.
- **Depuración por USB del Mega**: con el DIP switch en la fila **"Special solution"** de la tabla del fabricante (1, 2, 3 y 4 en ON, 5-7 en OFF, más el selector físico en RXD3/TXD3) el USB va directo a Serial0 del Mega A LA VEZ que Serial3 sigue activo con el ESP — permite ver el log (`DEBUG_SERIAL`, banner de arranque, cada heartbeat, cada frame recibido con hex) sin desconectar el enlace real. **No es "All independent"** (todos OFF) — esa fila no está confirmada para dar esta combinación. El log incluye `totalRawBytesFromESP`, útil para diferenciar "no llegan bytes físicamente al Mega" de "llegan pero el framing/protocolo falla".
- **Capa de abstracción "backend de tracción"**: interfaz común (`sendLocoCommand()`, `getTrackStatus()`, etc.) para que XpressNet (v1), LocoNet (v2) y DCC directo/central completa (v3) sean backends intercambiables sin reescribir el core Z21.
- **WiFi**: arranque en modo STA con fallback automático a AP propio (IP fija `192.168.0.111`) si no conecta.
- **Sniffer de depuración**: no está activo de forma permanente; se activa bajo demanda desde la web (WebSocket), con timeout/parada manual.
- **Pantalla 3.5" TFT**: sin touch, navegación por encoder rotativo (encoder aún no montado en el hardware actual). SD del shield usada como base de datos de locomotoras (CSV) y log de sesión.
- **Módulo de pantalla (v0.5)**: implementado en `src/mega_z21/display_*.h/.cpp`, deliberadamente fragmentado en varios ficheros pequeños en vez de uno monolítico — no reunificarlos sin motivo:
  - `display_types.h` — `DisplayStatusSnapshot` y `DisplayScreenMode` (sin lógica).
  - `display_theme.h` — colores, tamaños de texto, proporciones de layout (sin lógica).
  - `display_driver.h/.cpp` — único sitio que sabe inicializar el shield (`readID()`/`begin()`/rotación).
  - `display_layout.h/.cpp` — calcula los rectángulos de cabecera/divisor/log a partir de las dimensiones reales.
  - `display_status_panel.h/.cpp` — cabecera de estado (enlace ESP, red, frames, salud), con redibujado selectivo por fila para no parpadear.
  - `display_log_panel.h/.cpp` — buffer circular de líneas de log (sin `String` de Arduino, todo `char[]` fijo, para no fragmentar el heap del AVR).
  - `display_manager.h/.cpp` — fachada única (`displayInit()`, `displayTick()`, `displayLog*()`); es el ÚNICO header que `mega_z21.ino` incluye del módulo.
  - Cada fichero lleva su propio historial de versiones en la cabecera del archivo (fecha + qué cambió) — al modificar uno, añadir una entrada ahí, no reescribir el historial de los demás.
  - Diseño clave: el módulo de pantalla no lee ninguna variable global de `mega_z21.ino`; el sketch construye un `DisplayStatusSnapshot` (`buildDisplaySnapshot()`) y se lo pasa a `displayTick()`. Esto mantiene la pantalla desacoplada del protocolo Z21 y del framing con el ESP.
  - Como todavía no hay encoder ni botones, solo existe `SCREEN_MODE_DIAG` (vista fija en apaisado con cabecera de estado + log de comunicación) — pensada explícitamente para poder ver a simple vista si el gateway está listo y comunicando, sin cable USB. `SCREEN_MODE_LOCO`/`SCREEN_MODE_CONFIG` están reservados para cuando se monte el encoder; no implementarlos sin hardware real que los use.

- **Accesorios (agujas/señales/desacopladores/descarriladores, v0.11 mega / v0.13 esp)**: primer soporte de `LAN_X_GET_TURNOUT_INFO`/`LAN_X_SET_TURNOUT`/`LAN_X_TURNOUT_INFO` (PDF sección 5, "Switching"). A nivel de protocolo Z21 no hay diferencia entre una aguja, una señal de 2 aspectos o un desacoplador/descarrilador biestable: todos son "un decodificador de accesorios DCC de 2 salidas", así que un único `AccessoryState` (`traction/traction_types.h`) y unos únicos `setTurnout()`/`requestTurnoutRefresh()`/`getTurnoutState()` en `ITractionBackend` cubren los tres. Señales de más de 2 aspectos necesitan `LAN_X_SET_EXT_ACCESSORY` (PDF sección 5.4) — todavía no implementado, es el siguiente paso natural cuando haga falta. Direcciones de accesorio usan los 16 bits completos (sin el `& 0x3F` de las direcciones de loco), así que `AccessoryStateStore` (`traction/accessory_state_store.h`) usa `0xFFFF` como marcador de slot libre en vez de `0` (que sí es una dirección de accesorio válida). En el backend XpressNet, la conversión hacia `XpressNet.setTrntPos()`/`getTrntInfo()` y el callback `notifyTrnt()` están basados en el proyecto de referencia `tkoning/Z21-arduino` (ver sección 13 del spec) pero **sin confirmar contra hardware real todavía** (documentado explícitamente en `traction_backend_xpressnet.h`, punto 4 de "ASUNCIONES A VALIDAR") — si al probar con la MultiMaus la posición informada no coincide con la aguja real, revisar primero ahí.

## Convenciones de código

- **Dos sketches independientes**, un microcontrolador cada uno (toolchains distintos):
  - `src/esp8266_wifi/` — todo lo de red: WiFi (STA+fallback AP), servidor UDP Z21 (pasa datagramas al Mega sin interpretarlos), servidor web de configuración, autenticación del portal, sniffer por WebSocket.
  - `src/mega_z21/` — todo lo de la maqueta: núcleo del protocolo Z21 (interpreta los datagramas que llegan del ESP), backend de tracción (XpressNet en v1), pantalla, encoder, botón de parada, SD.
  - Se comunican por **Serial3** (pines 14/15 del Mega) con un protocolo simple `[LEN][payload]`. El ESP no debe interpretar el contenido Z21, solo transportarlo — toda la lógica del protocolo vive en el Mega.
- `src/shared/z21_protocol.h` es la fuente de verdad de las constantes del protocolo (HwType, headers de comando, etc.). Como los dos sketches usan cores distintos (ESP8266 vs AVR) no hay un mecanismo de include compartido automático en el IDE de Arduino — si se edita esta cabecera, replicar el cambio en ambos sketches (o copiar el archivo dentro de cada carpeta antes de compilar).
